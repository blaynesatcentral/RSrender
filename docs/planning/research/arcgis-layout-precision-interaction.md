# ArcGIS Pro Layout precision-interaction research

Status: evidence record for Wayfinder ticket #3  
Research date: 2026-08-13  
Benchmark: ArcGIS Pro 3.7 documentation and SDK surface (the current major/minor release at the time of research; [Esri lists 3.7.1 as the current patch](https://support.esri.com/en-us/knowledge-base/faq-what-are-the-build-numbers-for-releases-of-arcgis-p-000012500))  
Scope: selection, direct manipulation, precision aids, arrangement, clipboard/group/delete behavior, feedback, state, persistence, edge cases, and accessibility implications. This is a clean-room behavioral study; it does not reproduce Esri code, assets, branding, or trade dress.

## Executive findings

ArcGIS Pro's strongest reusable interaction ideas are the dual canvas/Contents selection model, exact geometry beside direct manipulation, independent snapping modes, persistent nonprinting guides, common-property multi-editing, and commands that work from both ribbon and context menu. Its precision model is not one coherent system, however: the current layout shortcuts use fixed point increments, bare arrow keys pan, the Spacebar both toggles selected-element visibility and temporarily disables snapping while dragging, and no page-design grid is documented. RSrender should preserve the concepts but make their state and scope more explicit.

The benchmark's alignment reference is the **first selected element**, whereas RSrender has already defined the visibly highlighted **Key Element** as the last selected element and keeps it fixed. That is an intentional, justified divergence: it makes the reference item inspectable and changeable rather than relying on hidden selection history.

The official sources establish the command surface much more completely than they establish pointer mechanics. They do not specify selection-handle count, rotation-handle geometry, hit-testing of overlaps, drag thresholds, or most modifier-key constraints. Those details remain observation/prototype work, not facts to infer from familiarity with other design applications.

## Method and evidence levels

- **D — documented behavior:** stated in current Esri help.
- **S — exposed surface:** named in Esri's ArcGIS Pro 3.7 SDK UI manifest. This proves that the command/state exists, but not its pointer gesture or detailed geometry.
- **I — inference:** a bounded conclusion drawn from the documented surface. It is not represented as observed ArcGIS behavior.
- **O — observation required:** a behavior the official material reviewed does not resolve. It needs a clean-room session with a licensed current ArcGIS Pro build, recorded as steps, build number, input device, result, and screenshot/video where permitted.

A licensed ArcGIS Pro executable was not available in this workspace. Consequently, this pass uses current first-party behavioral documentation and Esri's published UI command manifest as evidence, and explicitly routes unresolved pointer behavior to clean-room observation rather than presenting remembered or cross-application conventions as fact.

## Interaction-state model inferred for specification work

The sources imply at least the following mutually relevant states. This is an **inference**, not an Esri architecture claim:

1. **Navigate page:** bare arrows and navigation shortcuts change the view.
2. **Select elements:** canvas/Contents establish a selection, with create/add/remove/intersect modes exposed by the 3.7 command manifest.
3. **Transform selection:** pointer drag or Size & Position changes editable selected elements; snapping and drag modifiers alter the transaction.
4. **Edit component/subpart:** multipart child selection changes available commands; an activated map frame reroutes navigation.
5. **Edit text/vertices:** specialized edit modes own keystrokes until committed/canceled.

RSrender should not expose modes only through cursor changes. Each transient mode needs a name, visible boundary, allowed commands, commit/cancel behavior, and accessible announcement. Input precedence should be specified for at least: active text edit, active drag, active guide drag, active semantic-component edit, selection present, and canvas navigation.

## Clean-room observation backlog

The following questions cannot be answered responsibly from the reviewed first-party text. They should be tested against a licensed ArcGIS Pro 3.7.x build without inspecting code or assets:

1. Exact single-click, Ctrl-click, Shift-click, marquee, and touchpad selection gestures; whether clicking an already selected item changes selection order/reference.
2. Overlap hit-testing order and any cycle/select-from-list mechanism.
3. Selection adornment colors, handle count and placement for each element geometry, high-DPI hit areas, and cues distinguishing the first-selected alignment reference.
4. Free-rotation handle/pivot location; modifier keys; angle snapping; whether the Position Anchor and rotation pivot are the same concept.
5. Shift/Alt/Ctrl effects during move and resize, including precedence with aspect lock and Ctrl-drag duplication.
6. Live movement/size/angle readouts and whether values reflect snapped, pointer, or committed geometry.
7. Smart-guide cues, snap threshold versus zoom, multiple simultaneous candidates, tie-breaking, and whether hidden/locked elements remain snap targets.
8. Persistence and dirty-state behavior for snapping modes, ruler visibility, guide visibility/positions, selection, and active alignment-to-page state.
9. Undo coalescing for drags and property typing, undo behavior for guides/grouping/visibility/lock, and history after save/reopen.
10. Keyboard focus/announcement behavior in Contents and Element pane with Narrator/JAWS, especially mixed multi-selection, lock, hidden state, and geometry changes.

For each observation, record the ArcGIS build, Windows build/scaling, input device, starting state, exact steps, expected/actual result, and whether behavior is discoverable without prior knowledge. Screenshots should be used only as research evidence and must not become RSrender assets.

## Decision consequences for RSrender

These findings resolve the benchmark side of several already-grilled product decisions:

- Preserve ArcGIS's page-space precision concepts—direct manipulation plus exact fields, rulers, guides, smart alignment, and context-local commands—but implement them with RSrender terminology and visuals.
- Keep RSrender's explicit **Key Element** model. ArcGIS's first-selection rule proves that a stable reference is valuable; the lack of documented reference feedback is a reason to make ours more visible.
- Keep **Position Anchor** separate from Layout Pins and rotation pivot. ArcGIS evidence supports only the nine-point position/resize anchor.
- Treat lock as one consistent **Effective Lock State**. ArcGIS's ability to modify a locked element through the pane is unsuitable if users understand lock as protection from changes; the RSrender spec must enumerate properties that remain editable, if any.
- Build independent snap toggles for page, margins, guides, element edges/centers, text baselines, region/column boundaries, grid, and depth ticks. ArcGIS directly supports only the first four classes (with element smart guides combining edges and centers).
- Do not copy ArcGIS's fixed 1-point/5-point nudge increments. RSrender's document-unit increments are more transparent for physical log design and must be shown in shortcut help.
- Provide both equal-gap and equal-center distribution. Preserve outer/reference anchors visibly and preview span expansion when equal gaps cannot fit.
- Treat Contents and Properties as the accessible semantic representation of the canvas. Direct manipulation remains a convenience, not the only route to any core result.
- Define state-dependent shortcut routing explicitly. The ArcGIS Spacebar collision illustrates how a useful convention becomes hazardous when mode is not obvious.

## Ticket-level conclusion

The documented ArcGIS Pro Layout interaction surface is now decomposed into implementable atomic behaviors, intentional RSrender adaptations, and a finite observation backlog. No unresolved item above should be silently answered by “ArcGIS-like.” The next specification/prototype work should use the matrix IDs as traceable capability references and either adopt, adapt, defer, or reject every remaining **O** item before implementation.
