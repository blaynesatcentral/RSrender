[Esri Support — ArcGIS Pro build numbers](https://support.esri.com/en-us/knowledge-base/faq-what-are-the-build-numbers-for-releases-of-arcgis-p-000012500) The cited Arrange and Finish tutorials identify their demonstration environment as ArcGIS Pro 3.6 and state that behavior may differ in other versions; demonstration evidence is therefore version-bounded. ## Outcome

This ledger turns the remaining ArcGIS Pro Layout ambiguities into a finite clean-room research program. It does not treat “ArcGIS-like” as a requirement, and it does not make undocumented behavior authoritative. Each row is either:

- closed by official written evidence or a directly exhibited first-party tutorial;
- closed by an already settled RSrender product decision;
- open as a reproducible test for an authorized licensed ArcGIS Pro session; or
- deferred because the result cannot affect the MVP destination.

The ledger cross-references the existing [document-model report](./arcgis-layout-document-model.md), [precision-interaction report](./arcgis-layout-precision-interaction.md), and [elements/properties/dynamic-content report](./arcgis-layout-elements-properties-dynamic-content.md). Ticket #5’s text-flow research and ticket #6’s lifecycle/navigation/export/accessibility research are referenced by topic because their atomic identifiers were not available when this ledger was written. Their evidence should close rows here rather than create an unbounded second observation backlog.

## Evidence and priority vocabulary

| Label | Meaning |
|---|---|
| **Written** | An official Esri help, API, accessibility, or support source explicitly states the behavior. |
| **First-party demonstration** | An official Esri tutorial directly instructs or visibly exhibits the behavior. This is demonstration evidence, not a claim of hands-on observation by the RSrender team. |
| **Open—licensed observation** | Written sources leave a product-significant ambiguity. Run the scenario in an authorized installation and preserve the capture envelope below. |
| **Closed—RSrender decision** | The benchmark answer cannot change the settled RSrender behavior; the row records a deliberate clean-room divergence or a native RSrender requirement. |
| **Deferred** | The behavior is outside the initial product destination or too cosmetic to justify observation before MVP. |

Priority is based on decision impact, not how prominent an ArcGIS control appears:

- **P0** — can change the domain model, command/undo architecture, accessibility contract, PDF acceptance criteria, or a behavior users must never have to guess.
- **P1** — can materially improve efficiency, predictability, or test coverage without changing the product foundation.
- **P2** — benchmark polish or a deferred feature; observe only when a later phase brings it into scope.

Absence from the help is not evidence that a behavior is absent from ArcGIS Pro. Conversely, an ArcGIS behavior is evidence for a design option, not permission to copy its visual expression.
No ledger row is closed by inference alone. An inference may explain why a test is valuable, but closure requires written evidence, direct first-party demonstration, a reproducible licensed observation, or an explicit RSrender product disposition.

## Required capture envelope

Every licensed observation must include all applicable fields. A result without this envelope remains anecdotal and does not close a row.

| Area | Required capture |
|---|---|
| Product | ArcGIS Pro version and full build; license level; installed language; active theme; relevant application and project options. Esri’s official build table is the authority for mapping version to build. [Esri Support — ArcGIS Pro build numbers](https://support.esri.com/en-us/knowledge-base/faq-what-are-the-build-numbers-for-releases-of-arcgis-p-000012500) |
| Operating environment | Windows edition/build, regional format, keyboard layout, monitor resolution, monitor DPI, OS scaling, ArcGIS UI scaling, GPU and driver. |
| Input | Mouse model/settings, touchpad and gestures if tested, keyboard, modifier-key sequence, and whether Windows Mouse Keys or assistive input was active. |
| Document fixture | Fixture identifier and hash, page preset/dimensions/units/orientation, ruler origin, margins, guides, snapping settings, fonts installed/missing, element geometry and z-order, and map-series state where applicable. |
| External state | Default printer/driver and printable area; export destination type (local, read-only, network, or sync-backed); PDF viewer and PDF inspection tool/version; data-source availability. |
| Accessibility | Screen reader and version, verbosity settings, high-contrast theme, UI scale, reduced-animation setting, focus start position, and exact keyboard sequence. |
| Evidence artifact | Timestamp, observer, numbered steps, expected/actual result, before/after screenshots, short video when timing or focus matters, exported output/project copy where permitted, checksums, and a statement of whether the result reproduced twice from a clean fixture. |

Use at least two display configurations for geometry-sensitive tests: 100% scaling on a standard-density display and 150% or 200% scaling on a high-density display. Use a second current ArcGIS patch only when the result would otherwise define an RSrender contract and appears version-sensitive.

## Common synthetic fixture

Create one synthetic project from independently authored, non-client data. It should contain:

1. A custom-size layout with known margins, visible and hidden guides, and snapping enabled.
2. Three nested groups with uniquely named rectangle, line, picture, straight-text, and rectangle-text elements.
3. Two partially overlapping elements, two same-sized elements, one rotated element, one locked element, one hidden element, and one child whose local visibility differs from its ancestor.
4. Static text; wrapping rectangle text; intentionally overflowing text; valid, empty, type-invalid, stale-source, and deleted-source dynamic-text candidates; mixed inline formatting; an installed font and a deliberately missing font.
5. A small vector graphic, raster picture with transparency, and elements that extend just inside and just outside the page.
6. A simple map frame and map series only for benchmark scenarios that cannot be expressed with ordinary layout elements.

Record all starting geometry and properties in physical page units. Reset from the unchanged fixture before every scenario so undo history, selection order, pane state, and prior snapping do not contaminate results.

## Execution frontier

Run only the tests that can still affect a specification decision. The useful initial frontier is:

1. **Interaction/Contents batch:** OB-CT-01, CT-03, CT-04, SM-01, SM-03, SM-05, SM-06, SM-07, SM-09, and SM-10. One controlled screen recording can cover shared pointer and command-history evidence, but each row still gets a separate result record.
2. **Properties/text batch:** OB-PD-01, PD-02, PD-04, PD-05, PD-07, and PD-09. Coordinate PD-07/PD-09 with ticket #5 so the same fixture and terminology are used.
3. **Lifecycle/export batch:** OB-PG-01, PG-04, NE-03, NE-05, NE-06, NE-08, and NE-09. Coordinate with ticket #6; RSrender’s own storage/PDF prototypes ultimately carry more weight than benchmark quirks.
4. **Accessibility batch:** OB-CT-07, NE-11, NE-12, NE-13, and NE-14. Execute with an accessibility practitioner when possible and retain transcripts, not just screenshots.

P1 tests can run in unused time after their related P0 fixture is open. P2 behavior must not delay product specification. A patch update does not require repeating the entire program: rerun only scenarios whose release notes, results, or dependencies suggest a material change.

## Resolution and handoff rules

For each open row, attach an evidence record containing the capture envelope, steps, artifacts, result, and one of these dispositions:

- **Adopt concept** — name the neutral interaction principle and translate it into RSrender domain language.
- **Adapt** — state the ArcGIS evidence, the different RSrender constraint, and the resulting product rule.
- **Reject/diverge** — cite the settled RSrender decision and explain why benchmark parity would be harmful or ambiguous.
- **No decision impact** — close the row and do not turn cosmetic observation into implementation scope.
- **Still unresolved** — identify the single missing variable and a bounded follow-up scenario; do not write “needs more research” without a test.

A row closes only when the result has an explicit specification destination or an explicit no-impact disposition. Raw screenshots, videos, or “ArcGIS does X” notes do not close it. If official written evidence and a licensed run differ, record the product version/build and treat the discrepancy as version-specific; do not generalize it to all ArcGIS releases.

## Clean-room guardrails

Allowed evidence collection is limited to ordinary, authorized use of a licensed application; official Esri help, tutorials, accessibility conformance reports, release notes, and support pages; independently authored synthetic fixtures; and screenshots, screen recordings, exported files, accessibility trees, and UI automation that exercise normally exposed user actions. Evidence artifacts are research records only.

The research program must not:

- decompile, disassemble, debug, memory-inspect, or reverse engineer ArcGIS binaries;
- inspect undocumented proprietary project serialization, intercept private network traffic, or bypass licensing/access controls;
- extract or reuse Esri source code, icons, fonts, templates, tutorial assets, symbols, screenshots, product strings, or proprietary file structures in RSrender;
- trace pixels, reproduce distinctive visual styling, copy branding/trade dress, or use visual similarity as acceptance criteria;
- infer implementation architecture from timing or UI behavior; or
- describe an official tutorial as an RSrender team hands-on observation.

The evidence record should describe neutral semantics—such as “the first selected object remains fixed during left alignment”—and omit ornamental details unless color, size, focus, or motion is material to accessibility. An independent specification pass must translate all adopted behavior into the RSrender ubiquitous language and domain model before implementation. No engineer should need the ArcGIS application or an Esri asset to implement or verify an RSrender acceptance test.
